# KoCaseImport 0.2.6

헌법재판소 공식 자료를 Commons와 한국어 위키문헌으로 가져오는 Toolforge용 Python 도구입니다. 웹 이용자는 Wikimedia OAuth2로 로그인하고 자신의 최근 작업과 간단한 처리 결과만 볼 수 있습니다.

## 변경 내용

### 0.2.6: 재시작 후 로그인·작업·사용량·파일 유지

**0.2.5에서 처음 전환할 때는 단순 재시작부터 하지 마세요.** 기존 `/tmp` 자료를 옮기기 전에 컨테이너를 교체하면 복구할 수 없습니다. [영속 저장 전환·운영 가이드](PERSISTENCE-GUIDE.md)의 순서대로 이전 파일 생성 → 새 빌드 → 영속 DB 초기화·가져오기 → `--mount=all` 시작을 진행합니다.

- Toolforge에서는 비공개 ToolsDB(MariaDB)에 세션, 암호화된 OAuth 토큰, 작업 결과와 최근 24시간 사용량을 저장합니다. PDF·결과 파일과 관리자 요청 로그는 `$TOOL_DATA_DIR/kocaseimport-data` 아래 비공개 공유 폴더에 보관합니다. SQLite는 로컬 개발용으로 유지합니다.
- 최초 설정 후에는 새 빌드와 서비스 재시작만으로 기존 데이터를 계속 사용합니다. 로그인 유효기간 12시간, 작업 7일, PDF 24시간, 관리자 로그 최대 30일·20MiB는 재시작으로 연장되지 않습니다. 브라우저 종료 후 장기 로그인 기능은 추가하지 않았습니다.
- 기존 `KOCASE_SECRET_KEY`, `KOCASE_TOKEN_KEY`, OAuth 키, API 키, 관리자 ID를 그대로 유지합니다. 저장된 키 지문, 스키마 버전, DB와 파일 폴더의 식별자가 다르면 기동/접수를 거부합니다. 비공개 DB 이름과 NFS 마운트를 검사하며 빈 SQLite·로컬 폴더로 자동 대체하지 않습니다.
- DB의 트랜잭션 잠금으로 접수 한도·상태 변경을 직렬화하고, 저장 크기는 트리거로 제한합니다. MariaDB에서는 데이터의 논리 크기를 256MiB로 제한하며 인덱스·엔진 오버헤드는 별도입니다. 조회 기록 삭제·사용량 유지·관리자 접근 검사는 계속 적용됩니다.
- 사용자별 토큰 갱신은 짧은 DB 갱신과 별도의 잠금으로 처리합니다. 외부 인증 통신 중 전체 작업 DB를 잠그지 않으며, 그 사이 로그아웃하면 새 토큰을 저장하지 않습니다.
- DB 실행권은 감독 워커가 5초마다 갱신하고 60초 후 만료됩니다. 하나의 워커만 작업을 가져가고, 이전 워커는 실행권을 잃으면 후속 API 호출·DB 갱신·다운로드를 중단합니다. 재시작 당시 실행 중이던 작업은 실패 상태로 남겨 확인하게 하며 자동 재게시하지 않습니다. 대기 중 작업은 로그인 유효기간 내에서 계속 처리합니다.
- 시작 스크립트가 웹·워커·작업 자식을 함께 종료합니다. 이미 외부 서버에 전송된 요청까지 취소하거나 DB와 외부 위키 사이의 완전한 단일 트랜잭션을 보장하지는 않습니다. 중단 작업은 공용·위키문헌의 실제 게시 결과를 확인해야 합니다.
- 이전 파일은 경로·파일 종류·크기·해시·기존 키를 검증하고 빈 DB에만 가져옵니다. 기존 만료 시각과 사용량을 유지합니다. 원본을 잃어 새 DB만 만드는 경우와 오래된 백업을 복원한 경우에는 사용량 우회를 막기 위한 24시간 보호 대기를 적용합니다.
- 기본 ToolsDB 접속은 Toolforge 내부 호스트를 사용합니다. 외부 DB를 별도로 쓸 때는 `KOCASE_DB_SSL_CA`로 서버 인증서와 호스트명을 검증해야 합니다. TLS 검증 실패 시 평문 연결로 전환하지 않습니다.

SQLite 회귀 검사와 실제 MariaDB 통합 검사를 함께 제공하며, 외부 Wikimedia API는 모의 응답을 사용합니다. 실제 프로세스 재시작, 로그인 유지·로그아웃, 동시 한도, 갱신 중 로그아웃, 워커 실행권, 저장 한도·장애, 파일 이전·경로 공격을 검사합니다. 운영 Toolforge에 배포하거나 외부 위키를 수정하는 테스트는 자동 수행하지 않습니다.

### 0.2.5: 선택 삭제와 관리자 요청 기록

- 자신의 최근 작업에서 완료·실패한 작업을 선택해 삭제합니다. 작업 상세 화면에서도 한 건씩 삭제할 수 있습니다. 확인 화면에서 대상 사건·작업을 확인한 뒤 삭제합니다.
- DB의 해당 작업 행(사건 정보, 결과, 상세 로그 포함)과 서버의 해당 작업 폴더(PDF, manifest, 부분 파일)를 삭제합니다. 이후 상세 조회·PDF 다운로드·Dry-run 후속 게시가 불가능합니다. 이미 Wikimedia Commons·위키문헌에 게시한 자료는 삭제하지 않습니다.
- 삭제해도 서버 시각 기준 최근 24시간 사용량은 줄지 않습니다. 사용량 집계에는 사용자 고유 ID·작업 식별자·접수 종류·접수 시각만 남고 사건번호·PDF·결과는 남기지 않습니다. 기존 정리 작업이 24시간 경과 집계를 제거합니다.
- 관리자용 서버 요청 로그에는 사용자명·Wikimedia 고유 ID, 사건번호·작업 ID, 요청 종류·시각·모드·종료 상태만 남깁니다. 토큰·쿠키·API 키·OAuth 코드·PDF 주소·원문·IP·User-Agent·상세 오류는 기록하지 않습니다.
- 기록 대상은 새로 접수하는 사건 준비, 후속 게시, 작업 종료, 사용자 삭제 요청·완료, 관리자 기록 열람입니다. 일반 페이지 접속과 익명·권한 거부·형식 오류·한도 거부 요청은 요청 로그를 만들지 않습니다. 반복 게시 버튼 클릭도 새 접수로 기록하지 않습니다.
- 관리자 화면은 인증된 OAuth 중앙 사용자 ID를 서버의 허용 목록과 대조하여 매번 권한을 검사합니다. 기본 관리자 없음이며, 사용자명·첫 로그인 계정·URL·쿠키의 관리자 표시는 권한 부여에 사용하지 않습니다. 관리자는 다른 사람의 PDF·상세 로그를 보거나 작업을 삭제할 권한을 추가로 얻지 않습니다.
- 로그는 DB 테이블이 아닌 전용 JSONL 서버 로그입니다. 기본 경로는 `KOCASE_DB_PATH`의 상위 폴더 아래 `audit/`이며, 최대 30일·파일당 2MiB·10개로 제한합니다. 용량 한도나 로그 묶음의 만료에 따라 더 일찍 지워질 수 있습니다. 파일은 0600, 폴더는 0700입니다.
- 관리자 화면은 최근 100건씩 이전 기록을 볼 수 있으며, Wikimedia 고유 ID와 사건번호로 정확 일치 검색을 지원합니다. 기본 화면의 별도 목록에는 현재 DB에 보관 중인 최근 100개 작업도 보여 주어 업데이트 전 작업을 확인할 수 있습니다. 과거의 요청 이벤트를 소급 작성하지는 않습니다.

**관리자 등록**

1. 업데이트한 앱에 본인 Wikimedia 계정으로 로그인합니다.
2. 상단 사용자명을 눌러 **내 계정 → Wikimedia 고유 ID**의 숫자를 확인합니다. 이 값은 계정명이나 OAuth 클라이언트 ID가 아닙니다.
3. Toolforge의 해당 도구 계정에서 다음을 실행하고 프롬프트에 위 숫자를 입력합니다. 여러 관리자는 쉼표로 구분합니다.

```bash
toolforge envvars create KOCASE_ADMIN_USER_IDS
toolforge webservice buildservice restart
```

4. 같은 계정으로 접속하면 상단에 **관리자 요청 기록** 링크가 표시됩니다. 등록된 ID가 없으면 누구에게도 관리자 화면을 허용하지 않습니다. 추가 OAuth 권한이나 키 재발급은 필요하지 않습니다.

**삭제와 감사 로그의 보안·운영 범위**

- 삭제는 POST, 로그인, CSRF, 확인 체크를 요구합니다. 최대 30개를 처리하며, 최종 삭제 트랜잭션 안에서 모든 작업의 소유자와 완료·실패 상태를 다시 검사합니다. 하나라도 다른 사용자·누락·진행 중 작업이면 선택 전체를 거부합니다.
- 삭제와 후속 게시가 경쟁하면 먼저 DB 상태를 확정한 요청만 진행합니다. 실행 중인 작업은 종료된 뒤 삭제해야 합니다. 파일 작업 잠금을 즉시 얻지 못하면 HTTP 409로 재시도를 안내합니다.
- 삭제 경로는 검증한 작업 ID로만 구성하고 사용자 제공 PDF 경로는 사용하지 않습니다. 심볼릭 링크의 대상은 삭제하지 않으며 Linux의 디렉터리 FD 기반 삭제를 사용합니다.
- 접수·삭제 요청 로그를 디스크에 기록할 수 없으면 해당 요청을 거부합니다. 파일 삭제가 실패하면 DB 작업 행을 유지하며 성공으로 표시하지 않습니다. 여러 파일 중 일부가 이미 삭제되었어도 다시 요청하여 나머지를 정리할 수 있습니다.
- 파일시스템과 SQLite는 하나의 트랜잭션이 아닙니다. 서버가 중간에 종료되면 파일이 일부 삭제되고 DB 행이 남을 수 있으며, 이때 목록에서 다시 삭제할 수 있습니다. 완료 로그 쓰기에만 실패한 경우에도 먼저 기록한 요청 로그는 남습니다. 로그의 ‘요청’ 자체가 DB 커밋이나 외부 게시 성공을 뜻하지는 않습니다.
- SQLite `secure_delete`를 켜서 삭제한 행의 DB 페이지 내용을 지우도록 합니다. 이미 내려받은 파일, 외부 위키, 운영자가 만든 백업, 파일시스템 잔존 데이터까지 소급 삭제하거나 복구 불가능성을 보장하지는 않습니다.
- 로그의 개행·제어 문자를 정리하고 JSON으로 인코딩합니다. 관리자 화면은 명시한 필드만 HTML 이스케이프하여 표시하고 모든 응답에 `no-store`를 적용합니다. 로그 파일·원시 JSON을 웹에서 직접 제공하지 않습니다.
- 로그는 운영자/애플리케이션 권한으로 수정 가능한 파일이며 변조 방지 보관소가 아닙니다. 해당 권한이 탈취되면 이 기능만으로 방어할 수 없습니다. 현재 단일 컨테이너·단일 감독 워커 구성으로 운영합니다.
- **0.2.5까지는 영속 DB 전환을 포함하지 않았습니다.** 당시 기본 `/tmp`의 DB·PDF·요청 로그는 컨테이너 교체 시 사라질 수 있습니다. 0.2.6에서는 위의 영속 저장 전환 가이드를 따르세요. 감사 폴더를 `public_html`, 작업 폴더 또는 그 하위 경로로 설정하지 마세요. 키·DB 덤프·요청 로그는 소스 압축파일이나 공개 저장소에 포함하지 않습니다.

검증: 기존 기능 및 새 권한·삭제·동시 게시 경쟁·심볼릭 링크·파일/감사 기록 실패·로그 회전·만료·페이지 이동·관리자 출력 검사를 포함한 55개 테스트가 모의 API 환경에서 통과했습니다. 실제 Toolforge 계정에 배포하거나 외부 위키에 게시한 검증은 별도입니다.

보안 설계 참고: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

### 0.2.4: 과거 사건번호와 실패 원인 표시

- `97헌가12`를 `1997헌가12`로 확장하지 않고 API의 `eventNo`에 `97헌가12` 그대로 보냅니다. `97 헌가 12`도 같은 사건으로 처리합니다. `1997헌가12`로 입력한 경우에는 `97헌가12`로 정리하며 API 응답 비교에도 같은 규칙을 사용합니다.
- 2000년 이후 네 자리 사건번호는 그대로 유지합니다. 기존 `24헌마123등` → `2024헌마123등` 축약 입력도 유지합니다. 두 자리 또는 네 자리 연도만 허용하고 세 자리 연도는 거부합니다. 입력 화면에도 과거 사건번호 예시를 추가했습니다.
- 실패 결과에 **중단 단계·원인·다음 조치**를 표시합니다. 실제 예외 문자열, 원시 API 응답, 인증키, 다운로드 토큰, 서버 경로, traceback은 HTML에 전달하지 않습니다. 검증한 오류 코드·HTTP 상태·숫자 API 결과 코드와 정해진 안내문만 사용합니다.
- **PDF 미제공**은 조회에 성공한 자료에서 PDF 파일 정보를 찾지 못한 경우에만 표시합니다. HWP가 제공되는 판본도 함께 안내합니다. 판례집·공보 대체 사용이 꺼진 경우는 별도로 표시합니다.
- 일부 상세 조회가 실패하면 **PDF 제공 여부 확인 실패**로 표시하고 조회 실패 원인을 덧붙입니다. 통신 실패를 PDF 부재로 단정하지 않습니다.
- PDF 다운로드 중에는 HTTP 404/410(주소의 파일 없음), 다른 HTTP 오류, 연결 중단, HTTPS 오류, 시간 초과, 빈 응답, PDF가 아닌 응답, PDF 읽기·암호화 문제, 크기·쪽수·보관 공간 한도를 구분합니다.
- 로그인 인증 오류, 파일 권한 오류, 전체 작업 시간 초과, 작업 메모리 부족, 서버 재시작 및 프로세스 비정상 종료도 구분합니다. 원인을 확정할 수 없는 종료는 임의로 PDF 부재나 메모리 부족으로 표시하지 않습니다.
- 진행 중에는 `PDF 주소 확인 중`, `다운로드 중`, `PDF 검증 중`을 표시합니다. 이미 성공한 PDF 다운로드나 공용 게시 링크는 후속 실패가 발생해도 유지합니다.
- 이전 버전의 실패 작업에는 상세 원인이 저장되어 있지 않아 과거 원인을 복원할 수 없습니다. 업데이트 후 새 작업을 실행하면 구체적인 원인을 확인할 수 있습니다.

기존 저장소에 변경 사항을 반영한 뒤 재빌드·재시작하면 됩니다. 새 환경변수나 OAuth 권한은 필요하지 않습니다. 0.2.3의 세션·자원·24시간 한도와 위키문헌 서식은 계속 적용됩니다.

### 0.2.3: 세션·작업 자원 제한과 위키문헌 본문 서식

**익명 세션 저장소 소진 방지**

- 쿠키 없는 일반 요청, 잘못된 주소 접근, 로그인 시작 요청은 서버 세션 행을 만들지 않습니다. 익명 CSRF 값은 Flask 서명 쿠키에, OAuth 로그인 준비 정보는 암호화한 쿠키에만 담습니다.
- OAuth 인증과 사용자 확인이 성공한 뒤에만 서버 세션과 토큰을 같은 트랜잭션에서 저장합니다. 로그인 준비 정보는 10분 유효하며 성공한 state는 재사용을 거부합니다. 로그아웃 시 토큰은 즉시 비우고 재사용 방지 기록만 최대 10분 더 유지합니다.
- 세션·토큰 만료 인덱스를 추가하고, 정리는 요청 경로에서 제거했습니다. 단일 워커가 주기적으로 최대 500행씩 정리합니다. 이전 버전의 익명 세션도 정리 대상입니다.
- 세션 및 토큰은 각각 서버 전체 최대 5,000개, 사용자별 최대 10개입니다. 한도를 초과하면 추가 로그인을 거부합니다.

**서버 시각 기준 최근 24시간 이용 한도**

- 사용자 식별 기준은 Wikimedia 중앙 사용자 ID입니다. 브라우저 쿠키를 바꾸거나 다시 로그인해도 한도를 공유합니다. 자정 초기화 방식이 아니라 각 접수 시각으로부터 24시간을 계산합니다.
- 사건 1건을 1개로 셉니다. 그 사건의 색인·쪽별 문서는 별도 사건으로 세지 않습니다. `사건 준비`와 `실제 게시`에 각각 100건 한도를 적용합니다.
- 사건 준비: 새 작업 접수 횟수이며 Dry-run과 실제 게시 작업 모두 포함합니다. 실제 게시: 새 실제 게시 작업 또는 완료된 Dry-run에서 게시 버튼을 누른 횟수입니다. Dry-run 후속 게시는 사건 준비 횟수를 다시 차감하지 않습니다.
- 각 항목 80건부터 화면에 **limit 경고**, 100건에 도달하면 **limit 도달**을 표시합니다. 100번째 접수까지 허용하고 그 다음 요청은 HTTP 429와 Retry-After로 거부합니다. 게시와 준비 한도는 따로 적용됩니다.
- 접수 후 실패·로그아웃·시간 초과가 발생한 작업도 횟수에 포함합니다. 거부된 요청과 중복 게시 버튼 클릭은 횟수를 늘리지 않습니다. 한도 확인·횟수 예약·작업 등록은 하나의 SQLite 트랜잭션으로 처리합니다.
- 업그레이드 시 DB가 유지되어 있다면 최근 기존 작업도 한도에 반영합니다. **기본 `/tmp` DB가 컨테이너 교체로 사라지면 한도 기록도 사라집니다. 재시작을 넘어 엄격하게 보존하려면 DB와 작업 파일의 영속 저장 구성이 별도로 필요합니다.**

**자원 상한과 보관 정리**

| 대상 | 기본 상한 |
|---|---|
| 대기·실행 작업 | 사용자별 3건, 서버 전체 100건 |
| 작업 DB 기록 | 전체 2,000건, 종료 후 7일 보관 |
| PDF | 파일당 50 MiB, 최대 500쪽 |
| PDF·결과 파일 전체 | 1 GiB |
| 작업별 결과 데이터 | 512 KiB |
| SQLite DB | 256 MiB (기존 파일이 더 크면 즉시 축소하지 않음) |
| 종료한 작업의 PDF·결과 파일 | 마지막 작업 갱신 후 24시간 |
| PDF 다운로드 | 청크마다 총 120초 검사, 헤더 및 실제 수신 바이트 검사 |
| 작업 자식 프로세스 | 가상 메모리 256 MiB, CPU 및 전체 실행 시간 30분 |

다운로드는 프로세스 간 파일 잠금으로 보관 공간을 확인합니다. 초과·실패한 부분 다운로드는 삭제합니다. 작업은 별도 자식 프로세스에서 실행하므로 느린 응답이나 PDF 처리로 멈춘 경우에도 감독 워커가 시간 초과 후 종료합니다. 보관 정리는 작업 사이에 최소 60초 간격으로 실행하며, 실행 중인 작업의 파일은 삭제하지 않습니다. 과거 임시 디렉터리도 정리합니다. 위키에 이미 게시된 파일·문서는 삭제하지 않습니다.

**위키문헌 본문**

- `<pages index=...>` 앞에 `{{머리말}}`을 넣고 제목(사건번호), 부제(사건명), 저자(대한민국 헌법재판소), 연도(선고 연도), 설명(선고일·원문 판본)을 채웁니다. 확인되지 않은 값과 이전·다음·역자 등은 비웁니다.
- 머리말에는 `분류없음=true`를 지정합니다. `<pages>` 뒤에는 아래 코드만 분류·라이선스로 추가합니다. 라이선스 틀이 자체적으로 붙이는 관리 분류는 해당 틀의 동작을 따릅니다.

```wikitext
== 라이선스 ==
{{PD-South Korea-exempt}}

[[분류:대한민국 헌법재판소 판례]]
```

기존 문서는 `KOCASE_OVERWRITE=false`일 때 그대로 유지합니다. 이번 업데이트를 적용해도 기존 위키 문서를 일괄 수정하지는 않습니다.

0.2.2에서 업데이트할 때는 저장소에 변경분을 반영하고 재빌드·재시작하세요. OAuth 키와 콜백 주소는 그대로 사용합니다. DB 열·인덱스·한도 테이블은 시작 시 자동으로 추가합니다. 워커는 한 개만 실행해야 합니다. 기본 자원 상한은 `kocaseimport/config.py`에 명시되어 있습니다.

### 0.2.2: 게시 결과 링크와 Dry-run 후속 게시

- 결과 화면에 공용/위키문헌 업로드 상태를 추가했습니다. 실행 중에는 기존처럼 3초마다 화면을 갱신합니다.
- 공용 업로드 성공 직후 **공용 업로드 완료**와 **공용 파일 보기** 링크가 표시됩니다. 동일 파일을 발견한 경우에는 **공용 파일 준비 완료 · 동일 파일 재사용**으로 구분합니다.
- 색인·쪽별 문서·본문 처리가 모두 끝나면 **위키문헌 업로드 완료**와 **위키문헌 문서 보기** 링크가 표시됩니다. 이후 단계가 실패해도 이미 완료된 공용 링크는 유지합니다.
- 완료된 Dry-run 결과에 **내 계정으로 공용·위키문헌에 이어서 게시** 버튼을 추가했습니다. `KOCASE_LIVE_EDITS=true`이고 기존 PDF와 확인 자료가 남아 있을 때 사용할 수 있습니다.
- 버튼을 누르면 같은 작업이 실제 게시 대기 상태로 바뀌고 Dry-run 표시가 ‘아니요’로 변경됩니다. 확인했던 사건 정보와 PDF를 그대로 사용하며 재조회·재다운로드하지 않습니다. 게시 전에 파일 해시와 쪽수를 재검증합니다.
- 현재 로그인한 작업 소유자의 OAuth 인증을 사용합니다. CSRF를 검증하며 중복 클릭은 동일 작업으로 이동할 뿐 추가 작업을 등록하지 않습니다.
- 기존 DB에 필요한 열을 자동 추가합니다. 이전 버전의 완료 작업도 DB와 PDF가 보존되어 있으면 이어 게시할 수 있고, 완료된 게시 작업은 저장된 결과에서 링크를 복원합니다.
- MediaWiki 업로드·편집 응답이 성공인지 확인한 뒤에만 완료로 기록합니다. 상세 로그나 원시 응답은 결과 화면에 노출하지 않습니다.

0.2.1에서 업데이트할 때는 기존 OAuth 키·환경변수를 유지하고, 아래 소스 빌드 및 재시작만 수행하면 됩니다. 별도 OAuth 권한 추가나 키 재발급은 필요 없습니다. 실제 게시 기능을 사용하려면 `KOCASE_LIVE_EDITS=true`를 유지하세요. 재배포로 임시 기록이 사라졌다면 업데이트 후 새 Dry-run 작업으로 버튼을 확인합니다.

### 0.2.1: 받은 PDF 확인

- 작업 화면의 PDF 다운로드 항목에 **검증용 PDF 내려받기** 링크를 추가했습니다.
- Toolforge가 실제로 받은 파일을 그대로 내려받습니다. 원본 사이트로 이동하거나 PDF를 다시 받지 않습니다.
- PDF 다운로드·쪽수 확인이 끝나고 파일이 남아 있을 때만 표시합니다. Dry-run뿐 아니라 게시 진행 중·후속 작업 실패 시에도 사용할 수 있습니다.
- 로그인한 작업 소유자만 다운로드할 수 있습니다. 타인 작업은 404, 비로그인은 401입니다. 서버 경로나 상세 로그는 표시하지 않습니다.
- 기존 0.2.0 완료 작업도 DB와 PDF가 남아 있으면 지원합니다. 기본 저장소는 임시 디렉터리이므로 컨테이너 교체 후에는 새 작업으로 다시 받아야 할 수 있습니다.
- OAuth 권한이나 환경변수 추가는 필요 없습니다. 아래 배포 절차로 소스를 다시 빌드하고 재시작합니다.

### 0.2.0: OAuth와 사용자별 작업

- OAuth2 Authorization Code + PKCE(S256), 10분 유효·1회용 state 검증.
- Meta의 OAuth profile에서 확인한 중앙 사용자 ID(sub)로 작업 소유자 구분.
- 사용자별 access/refresh token 암호화 저장. 쿠키에는 임의 세션 식별자만 저장.
- 웹 작업의 양쪽 위키 API 요청은 신청자 토큰 사용. 공용 봇이나 전역 Bearer token으로 대체하지 않음.
- 자신의 최근 30개 작업. 타인 작업 주소 접근은 404, 비로그인은 401.
- 작업 화면: 사건 조회·확인, PDF 다운로드 결과·쪽수, 원문 판본, Dry-run 여부. 완료/후속 실패는 조회 상태에 짧게 표시.
- 전체 JSON, 상세 단계, 내부 경로, 로그, traceback은 사용자 HTML에 전달하지 않음.
- CSRF 검증, Secure/HttpOnly/SameSite 쿠키, 인증 후 세션 교체.
- 기본은 Dry-run. Dry-run도 로그인 필요.

## OAuth 애플리케이션 등록

https://meta.wikimedia.org/wiki/Special:OAuthConsumerRegistration/propose

- OAuth 2.0, confidential 웹 애플리케이션. owner-only가 아닌 여러 사용자가 승인하는 앱으로 등록.
- Authorization Code 및 Refresh Token 사용.
- 콜백: `https://실제도구이름.toolforge.org/oauth/callback` (정확히 일치).
- Commons와 한국어 위키문헌 모두 사용할 수 있는 프로젝트 범위.
- 사용자 식별, 필요한 문서 생성·편집 및 파일 업로드 권한. 식별 전용(authonly) 앱으로는 게시 불가.
- 등록자 계정으로 먼저 시험 가능. 다른 사용자 이용에는 Wikimedia 측 앱 승인 필요.

OAuth 앱은 직접 등록해야 하며 발급된 인증정보는 소스에 포함되어 있지 않습니다.

## Toolforge 업데이트

**0.2.6 최초 전환에는 아래의 과거 배포 순서보다 [영속 저장 전환 가이드](PERSISTENCE-GUIDE.md)가 우선합니다.** 영속 DB 이전을 완료한 뒤의 업데이트에는 기존 키를 유지한 재빌드·재시작만 필요합니다.

프로젝트 폴더 내용을 기존 Git 저장소 루트에 반영합니다. 중첩 폴더를 만들지 마세요. requirements.txt, 새 auth.py, store.py, 모든 templates를 포함해 전체 변경을 반영합니다. `.env`와 인증정보는 커밋하지 않습니다.

기존 CCOURT_OPENAPI_URL, CCOURT_SERVICE_KEY, CCOURT_CASE_PARAM=eventNo, CCOURT_ALLOW_PUBLISHED_PDF 설정은 유지합니다. getIncdntDetail에는 `type=json`을 보냅니다.

도구 계정에서 각각 실행하고 프롬프트에 값을 입력합니다.

```bash
toolforge envvars create MW_OAUTH_CLIENT_ID
toolforge envvars create MW_OAUTH_CLIENT_SECRET
toolforge envvars create MW_OAUTH_REDIRECT_URI
toolforge envvars create KOCASE_TOKEN_KEY
```

앞의 두 값은 앱 등록 시 발급받습니다. MW_OAUTH_REDIRECT_URI 예: `https://kocaseimport.toolforge.org/oauth/callback` (실제 도구 주소로 변경).

KOCASE_TOKEN_KEY 생성에는 표준 Python만 필요합니다.

```bash
python3 -c 'import base64,secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())'
```

출력값을 KOCASE_TOKEN_KEY 입력 프롬프트에 붙여 넣습니다. 이 키는 OAuth 토큰을 암호화하므로 공개하지 않습니다. 변경하면 기존 토큰을 읽을 수 없어 재로그인이 필요합니다.

KOCASE_SECRET_KEY도 32자 이상의 임의 문자열이어야 합니다. 기존 값이 이 조건을 만족하면 유지합니다. 필요할 때 생성·등록합니다.

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
toolforge envvars create KOCASE_SECRET_KEY
```

OAuth 설정이나 키가 누락되면 앱은 기동하지 않고 운영자 로그에 설정 이름을 알립니다. 최초 적용은 KOCASE_LIVE_EDITS=false를 유지합니다.

소스 커밋·푸시 후 실제 저장소 주소로 빌드합니다.

```bash
toolforge build start https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git
```

빌드 성공 후:

```bash
toolforge webservice buildservice restart
```

Procfile: `web: bash toolforge-start.sh`. 같은 컨테이너에서 웹과 워커를 실행합니다.

2. 사건 1건을 Dry-run으로 제출하고 자신의 목록과 결과를 확인합니다. PDF 다운로드 완료 후 **검증용 PDF 내려받기**를 눌러 실제 파일과 쪽수를 확인합니다.
3. 앱 승인 후 다른 계정에서 앞 계정 작업이 목록과 직접 주소 접근 모두에서 보이지 않는지 확인합니다.
4. 게시 시험 때 `KOCASE_LIVE_EDITS=true`로 등록하고 재시작합니다. 새 작업의 본인 계정 게시 확인란을 선택하거나, 완료된 Dry-run 결과의 **내 계정으로 공용·위키문헌에 이어서 게시** 버튼을 누릅니다. 재시작으로 임시 자료가 사라졌다면 먼저 새 Dry-run을 실행합니다.
5. 공용 완료 링크가 위키문헌 처리 중에도 표시되는지, 최종 완료 후 위키문헌 본문 링크가 표시되는지 확인합니다. 실제 위키에서 PDF·색인·쪽별 문서·본문을 확인합니다. 위키문헌 자동 전사는 ‘교정 안 됨’ 상태입니다.

웹 작업은 MW_BOT_USERNAME, MW_BOT_PASSWORD, MW_BEARER_TOKEN을 사용하지 않습니다. CLI에는 운영자용 인증 방식이 남아 있습니다.

## 세션과 기록

- 로그인 및 로컬 인증 연결은 최대 12시간. access token은 만료 전에 갱신하며 실패 시 공용 계정으로 전환하지 않습니다.
- 로그아웃은 현재 로그인에 연결된 로컬 토큰을 삭제하고 대기 작업을 중단합니다. 실행 중 작업의 다음 Wikimedia API 요청도 차단합니다. 이미 전송된 요청이나 완료된 편집은 되돌리지 않습니다.
- 로그아웃은 Wikimedia 전체 로그아웃이나 공급자 측 권한 철회가 아닙니다. 앱 권한 철회는 Wikimedia의 연결 앱 관리 화면에서 합니다.
- 같은 계정으로 다시 로그인하면 보존된 자신의 작업을 볼 수 있습니다. 실패 작업 자동 재개는 없으며 새 작업을 제출해야 합니다.
- 기존 0.1.1 작업은 소유자를 확인할 수 없어 누구에게도 배정하지 않습니다. 기록은 내부에 남지만 웹에서 숨기고 소유자 없는 대기 작업은 실행하지 않습니다.
- 상세 처리 기록은 내부 DB와 Toolforge 로그에만 남습니다. OAuth 토큰·인증 응답은 기록하지 않습니다. 예외는 작업 ID와 유형으로만 기록합니다.

## 배포 범위와 한계

OAuth/사용자별 작업/UI를 구현한 단일 컨테이너 버전입니다. 기본 DB는 `/tmp/kocaseimport/jobs.sqlite3`, 작업 파일은 `/tmp/kocaseimport/work`입니다. 컨테이너 교체 시 세션·토큰·기록·PDF가 유실될 수 있어 재로그인이 필요합니다. 별도 Job으로 워커를 분리하지 마세요. 완료된 Dry-run의 후속 게시와 사용량 제한은 지원하지만 ToolsDB 전환, 영속 저장, 실패·중단 작업 자동 재개는 포함하지 않았습니다. 워커 재시작 시 중단된 실행 작업은 실패로 처리합니다.

기존 판본 선택은 유지합니다. 결정문 PDF가 없으면 판례집·공보 PDF를 사용할 수 있고 판본을 표시합니다. 자동 전사는 교정 안 됨으로 생성하며 기존 문서는 기본적으로 덮어쓰지 않습니다.

Dry-run 완료는 사건 조회·PDF 다운로드·쪽수 및 SHA-1 확인 완료이며 게시·OCR 성공을 뜻하지 않습니다.

## 개발 및 검증

```bash
python3 -m venv venv
. venv/bin/activate
pip install -r requirements.txt
pip install pytest
pytest -q
```

테스트는 로컬 DB·테스트 키·모의 Wikimedia 응답을 사용합니다. 사용자별 접근 격리, state 재사용 차단, CSRF, 토큰 암호화·갱신·로그아웃, 웹 출력 제한, 워커와 양쪽 위키의 사용자 인증 전달을 검증합니다.

0.2.2에서는 공용/위키문헌 완료 링크의 순차 표시, 위키문헌 실패 시 공용 링크 보존, Dry-run 후속 게시의 접근 제어·중복 등록 방지·현재 인증 사용·PDF 재사용, 변경된 PDF 및 비활성화된 게시의 차단, API 미완료 응답 처리를 추가 검증했습니다.

0.2.3에서는 익명 반복 요청·로그인 시작 시 DB 행 미생성, 복사한 로그인 쿠키의 state 재사용 차단, 80/100건 경계와 24시간 만료, 동시 접수 경쟁, 한도 거부 시 트랜잭션 롤백, 후속 게시 별도 한도, 전체 대기·보관 상한, 큰 PDF의 중간 파일 정리, 만료 파일 정리·실행 중 파일 보존, 워커 자식 프로세스 시간 제한, 본문 머리말·라이선스·분류를 검증했습니다.

0.2.4에서는 두 자리 연도 정규화·API 요청·응답 대조, PDF 미제공과 조회 실패 구분, HTTP/연결/시간 초과/비PDF 응답 코드, 실제 PDF 검증 실패의 결과 표시, 실패 화면의 사용자별 접근 제한·인증정보 비노출 및 시간 초과 원인 기록을 검증했습니다. 모의 API 기준 전체 47개 테스트가 통과했습니다.

실제 client ID/secret이 제공되지 않아 실제 계정 로그인·승인·게시의 종단간 검증은 수행하지 않았습니다. Toolforge 직접 배포도 수행하지 않았습니다.
